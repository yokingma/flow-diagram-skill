# GitHub Release

本 Skill 供能够读取仓库文件和执行命令的 Agent 使用。在仓库根目录执行，先读[发布指南](../../../docs/releasing.md#4-发布到-github)和[版本说明规范](../../../docs/releases/README.md)。发布条件、命令和 CI 行为以指南及其引用的脚本、工作流为准。本 Skill 随仓库源码维护，位于生产 Skill 安装单元之外；WorkBuddy 使用独立发布流程。

默认按“准备”执行：交付候选文件和验收结果，不提交、推送或创建标签。用户明确要求“发布”时，按授权范围执行后续 Git 操作。技能被加载不等于获得发布授权；已针对同一候选给出的明确授权继续有效。

用户要求精简或修订已发布 Release 正文时，直接按[正文修订流程](../../../docs/releasing.md#修订已发布-release-正文)执行；准备或发布授权本身不包含修订其他已发布版本。

## 1. 确定候选

检查工作区、分支、`package.json`、本地标签和 `git remote -v`。核对 `origin` 的目标仓库后，刷新 `origin/main`，读取远程标签和 Release 状态。区分本次候选与其他任务的改动，列出同步 main 时会一并推送的提交；这些提交也必须在发布授权范围内。

使用用户指定的正式版本号；未指定时，根据已发布版本和实际变化提出建议，确认版本后再修改版本文件。已有同名远程标签或 Release 时，转入第 5 节核对现状，保留已有标签和附件；明确要求修改正文时走上述修订流程。远程、版本或候选范围不明确时，集中询问缺口。

完成条件：目标仓库、版本和拟发布的改动范围明确，已有版本与无关改动均已识别。

## 2. 准备版本与说明

从上一个正式发布标签到候选的实际差异整理变化；首次发布则概述当前能力。更新根 `package.json` 的分发版本，按[插件分发维护](../../../docs/development/flow-diagram-maintenance.md#plugin-distribution-maintenance)同步插件及 marketplace 元数据，将对应的 `CHANGELOG.md` 条目整理到本次版本，并撰写 `docs/releases/vX.Y.Z.md`。保留 SDK 运行时基线，除非本次发布明确包含已验收的 SDK 升级。

按[版本说明规范](../../../docs/releases/README.md)撰写简短的双语变更列表。验收详情保存在本次发布记录和 CI artifacts 中，向维护者单独报告。

完成条件：分发版本、全部插件及 marketplace 条目版本、变更记录和双语说明一致；每条说明对应本版实际变化，中英文逐项对应，需用户采取的升级操作已说明。

## 3. 验证并展示候选

先按[验收环境预检](../../../docs/releasing.md#验收环境预检)确定可用工具和真实目录，再在干净检出或独立候选副本中验收，保留原工作区的其他改动。按插件分发维护中的验收步骤检查插件候选；通用 ZIP 或 CI 通过不代表宿主插件已安装并可调用。检查候选文件的格式、引用及变更说明，记录受检内容和结果；候选后续变化时，重新执行受影响的检查。

展示目标仓库、版本、候选文件和未推送提交、Release 正文、已执行及未执行的检查。将已有发布授权与这份具体候选核对；授权范围不清楚时，完成可逆准备后再询问。

准备模式在此交付文件和结果。发布模式仅在检查通过且本次候选已获发布授权时继续。

## 4. 提交并触发发布

将提交、main 推送、标签创建和标签推送与各自的前置断言放在失败即停止的执行路径中；多命令 shell 使用 `set -euo pipefail` 或显式检查每一步退出码。前置检查失败后停止后续写操作，修复并重验后再继续。

核对暂存区，只提交本次候选文件，使用仓库规定的提交格式；候选已经提交时复用该提交。记录最终候选 SHA，确认提交内容与第 3 节的受检内容一致，且位于 main 历史中。核对远程地址和待推送提交后，同步候选到远程 main，刷新并确认 `origin/main` 已包含它。分支有分歧时保留现状，报告需解决的提交范围。

在最终候选 SHA 上创建附注标签。已有同名本地标签且目标相同时复用；目标不同时报告冲突，保留标签供维护者处理。在该提交的干净检出中按指南运行本地标签预检、构包和解包验收，确认 `HEAD` 与标签目标一致。全部通过后，只推送本次版本标签以触发 CI。main 推送成功但后续失败时，报告已经发生的远程变更，保留可恢复状态。

完成条件：远程版本标签准确指向已检查的候选，或已报告失败阶段及实际完成的 Git 操作。

## 5. 核对发布结果

确定该标签、候选 SHA 对应的运行 ID 后，使用一个持续 watch 或定期状态查询跟踪到结束；仅在阶段变化或失败时追加日志查询。复用 main 验收时，保存来源运行链接、尝试号和验收范围，分别记录复用结果与标签构包结果。失败时查看对应任务日志，报告原因和下一步；等待、失败或取消均记录为尚未发布成功。上传失败留下草稿时，保留现场并说明处理选项，由维护者决定恢复方式。

成功后核对公开 Release 的版本、双语正文和附件，下载通用 Skill ZIP 与校验文件并复核摘要。按指南核对公开访问和干净项目安装；访问、安装或实际查看无法完成时分别列为未执行项。

完成条件：分别报告交付产物、程序检查、实际查看，以及未执行项和遗留问题；附候选 SHA、标签、CI 和 Release 链接。缺少远程访问、CI 日志、下载或宿主运行能力时，说明具体受限步骤和后续操作，保留尚未确认的状态。
