# Screenshot capture and visual inspection

Before submitting any review, read [the complete field contracts and unviewed template workflow](review-inputs.md). Invalid review input is rejected before version allocation or rendering.
Use `validate` while drafting. When intermediate HTML is needed, use `author --browser none`; capture the needed samples only after the draft is ready. Keep the same temporary `--output <task-workspace>/history` for capture and review, then [finalize](tool-contract.md#finalize-the-task).

`author` attempts previews after default JSON/HTML, optional SVG and any requested GIF attempt. For independent stage failures and cancellation, see [partial delivery](export.md#partial-delivery-and-history). It uses the skill's explicit, locked `playwright-core` dependency inside the isolated runtime. It creates a dedicated browser, context and page; it neither connects to nor closes a browser owned by the host or user. Success, failure and cancellation close the resources the command created.

## Prepared browser

Pass `--browser <executable>` or set `FLOWSVG_BROWSER_PATH` to an installed Chrome/Chromium executable. An explicit path has priority. The tool verifies file readability and execution permission before launch; an unusable path fails visibly without creating a browser profile. Otherwise the tool detects standard macOS/Windows install locations or Linux executable names on `PATH`. `--browser none` disables detection. The tool never downloads a browser. Common executable paths are `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` on macOS, `/usr/bin/chromium` on Linux and `C:\Program Files\Google\Chrome\Application\chrome.exe` on Windows; verify the actual path in this environment. Without one, default JSON/HTML and optional SVG still complete; screenshot capture and visual inspection remain unperformed. Install a browser separately when the user wants that check. Recapture HTML or SDK previews through `author` in a new revision; collect missing formal SVG/PNG surfaces with independent [artifact evidence](artifact-evidence.md).

## Inspection-only preparation

For visual diagnosis without authoring changes, select the inspection source before step 4:

1. **Existing task evidence:** select the explicit saved revision, name and history root through [input and parent selection](diagnostics-and-revisions.md#selecting-a-parent). Reuse its registered, readable HTML or preview screenshots for the requested scope. For existing SVG/PNG files, use [artifact evidence](artifact-evidence.md) to collect missing display conditions.
2. **JSON or a finalized delivery:** create a canonical [task workspace](tool-contract.md#task-workspace). Use the exact JSON bytes with `author --input <existing.json> --name <name> --output <task-workspace>/history --browser <prepared-executable>` to generate temporary HTML and screenshots. For a finalized Agent page, select its matching `diagram.html` with `--html` under [page continuation](tool-contract.md#continue-an-existing-page). These new captures cover the new files; historical exports or viewing records retain their original identity.
3. **Missing HTML or preview captures in an existing task:** run `author --from <selected-revision> --name <same-name> --output <same-task-workspace>/history --browser <prepared-executable>` to capture a new revision from the unchanged JSON and inherited page. Read its report before selecting review sources. This creates inspection materials without editing the selected history.

Keep the input design and bytes intact, including its effective theme; use the existing report's theme override when one was recorded. Run structural validation first when the input is unverified; blocking errors or an incompatible page stop capture and become diagnosis findings. If a browser or image viewer is unavailable, report the missing visual checks. Follow step 4 only for the requested surfaces, record actual viewing through [review inputs](review-inputs.md), and report findings, evidence locations and coverage gaps. Inspection-only work stops there and retains its workspace; publishing a replacement or correcting the diagram requires authorization for that work.

## Reproducible samples

For animated diagrams, the plan uses actual compiled beats. It prioritizes a full-view overview, timeline start and final frame within the selected budget. The overview is an inspection projection at time zero: focus actions are removed, while all non-camera actions and content remain. The source JSON and timeline samples retain the original focus actions. An export at a chosen time preserves that time’s actual visibility and camera, including focus. For static diagrams (`scenes: []`), the plan contains exactly one full-view frame at time zero; there are no timeline states or transitions to sample. Neither the overview nor an export means “all objects visible.” If the reader needs an all-visible explanation, propose a separate, source-faithful composition and obtain the user’s decision for any changed meaning; do not silently remove hide actions or restore hidden objects.

Additional candidates are content-change beat starts, transition midpoints, flow midpoints and other beat starts. Content changes have priority over midpoints and ordinary starts. For equal priority, earlier times have priority. The default maximum is 12 images, including the overview; `author --samples <count>` selects a different maximum from 2 through 100. `--samples 2` retains the overview and timeline start, with the final frame in `visual.plan.omitted`. `--samples 3` can retain the overview, start and final frame, but need not include an intermediate stage. `visual.plan.omitted` lists candidates outside the selected bound. All intervening times remain unsampled; a few images do not establish continuous coverage. The plan is identical for identical input, compiler behavior and sample count.

## Check the selected key stages

1. In the existing stage plan, choose the key stages needed to answer the reader's question: the initial state, important changes or transfers, and the final state. A key stage is an author-selected explanation checkpoint, not a requirement for one image per scene, beat or edge.
2. Read `compilation.beats` and `compilation.totalDurationMs` to locate those stages on the actual timeline. A single `flow` can replace its authored beat duration and shift later stages; see [effective flow duration](timeline.md#transfer-and-emphasis). For concurrent flows in one beat, one suitable image can cover the transfers when each route and marker is visible and distinguishable.
3. Compare each selected stage with `visual.plan.points`, `visual.plan.omitted` and `visual.capturedFrames`. An overview removes focus and cannot substitute for the actual focused state or timeline start. A planned point without a successful capture is still missing evidence.
4. For a missing stage, first try a larger `author --samples <count>` budget in a new revision from the explicit selected parent. Read the new plan and captures: a larger budget does not create arbitrary-time candidates. If the needed time is not a candidate or remains outside the supported budget, use an existing [timed SVG/PNG export](export.md#requested-svg-and-png) and [actual-file evidence](artifact-evidence.md), or inspect the actual HTML at that time or through playback. Record the surface and time range checked; a formal image does not cover HTML controls, captions or continuous motion.
5. Actually view the selected images and record their source revision, frame or artifact identity and time through the existing [review workflow](review-inputs.md). New captures start unviewed, including recaptures of an unchanged diagram. Earlier observations do not establish viewing of the new images. Keep the correspondence with the selected stages in the existing task notes; no additional stage form is required.

Finish this check when every selected stage has identified viewed evidence, or an explicit gap and its effect on the explanation. If supplementation cannot be completed, disclose the missing stage and affected surface or interval. Use the existing quality status and report its scope; this author check adds no mechanical blocker or narrative score. Programmatic time and identity checks establish those facts, while actual viewing supports judgments about readability, whitespace and narrative continuity. Assess pacing through actual playback and report sample-only inspection as limited to the viewed states.

## Actual offline HTML

For Agent-composed pages, inspect the whole outer page and its declared embedded player. Page headings, the short introduction, functional reading hints, spacing and responsive layout are part of HTML viewing; controls and SVG state are checked inside the managed frame. During Agent self-check, apply the [page completion checklist](delivery-contexts.md#page-completion-checklist). If the page contains a block outside the closed whitelist, describe it as an authoring issue and move or remove it before delivery; this is a review instruction, not a CLI or report validation rule. Captures and hashes identify the complete final HTML, not only the iframe content.

When HTML is part of the requested delivery, `author` opens the saved `diagram.html` in an owned offline browser context after writing it. The report records the exact HTML SHA-256, input/SDK/theme context, viewport and background, initial paused state, control values, external requests, playback advancement and screenshots for the same static or compiled timeline points. These facts describe the file and browser behavior; they do not mean a model viewed the screenshots. Record actual viewing through [Save the later judgment](#save-the-later-judgment). A missing browser leaves `checks.html: not-run` with an explicit reason.

Each captured point renders the public SDK SVG state at exact milliseconds, explicit theme and full motion. Playwright uses a 1440 × 1000 viewport, device scale factor 1, offline context and a dedicated static document. Capture waits for `document.fonts.ready`. Images use system fonts; the report records observed font readiness, font family and font-face errors. A ready font set does not prove every Chinese glyph exists. Missing glyphs, reading difficulty and platform differences require actual image inspection. Cross-system pixel equality is not promised.

## Actual model inspection

Capture success sets `visual.status: awaiting-review`. `checks.visual` stays `not-run` and `viewedFrames` stays empty until a later review. View the actual PNGs through the host's image viewer or image attachments. If neither capability is available, leave visual inspection unperformed and explain the limitation. Start with the overview, then inspect the saved timeline samples. For each viewed image, assess reading order, density, occlusion and narrative continuity. Record which images were actually viewed; describe unreadable glyphs or missing content explicitly.

Reviewing every captured frame completes the preview review scope only. Report partial viewing and observed issues explicitly. Use the returned `qualityCoverage` and [overall quality contract](tool-contract.md#revisions-and-reports) to interpret `completion.quality`; preview review cannot replace required HTML or formal SVG/PNG checks. A screenshot filename, successful export or nonempty PNG does not establish visual approval.

For each observed issue, follow [diagnosis and revision decisions](diagnostics-and-revisions.md): explain the issue and candidate corrections; ask when the choice changes meaning and apply already authorized mechanical corrections. Preserve failed capture evidence and partial screenshots. Submit observations of existing images through independent `review`; changed observations append a record and identical submissions reuse the verified record. A retry that regenerates HTML or SDK previews uses `author` and creates a new revision. Use independent `evidence` for formal-image capture recovery. Saved reports remain unchanged during the task. Successful finalization retains review facts and removes temporary screenshots and revisions unless history was requested.

## Questions for the four observations

Keep the existing four observation fields. Answer the questions that apply to each actually viewed image; put discovered problems in `issues` with candidate treatments for the user's choice.

| Field | Inspection questions |
| --- | --- |
| `readingOrder` | Can the reader identify the entry point, then trace each relevant arrow from its source through bends or shared segments to its arrowhead? In regular layouts, would alignment or a simple right-angle path improve a long diagonal? Do bent paths introduce excessive detours or ambiguous shared segments? Do group and component endpoints match the selected relationship scope? In a layer overview, are component exceptions justified? Are request and return directions distinct? Do boundary headings explain membership? Can the reader recover the direction after a crossing? |
| `density` | At the intended display width, can the reader distinguish labels, conditions and units? Does the slide's occupied area or article column leave enough space? Are short-content nodes oversized, or does their whitespace serve comparison, later animation content or the composition? Record actual or assumed dimensions. A higher-resolution file does not enlarge text displayed at the same width. Node count is a prompt to assess readability, never permission to delete information. |
| `occlusion` | Does a connection cross an unrelated node in a way that suggests a false relationship? Do long coincident paths hide independent edges, merge solid and dashed meanings or suggest an unsupported junction? Can each edge be followed through the busy channel in an actual crop? Does an edge label cover an unrelated node, another label or a needed arrowhead? Are text, group titles and ports clipped or covered? Distinguish intended containment and endpoint contact from obscured meaning. A crossing alone need not be an error. |
| `narrative` | Does the shown state match the selected time, caption and explanation? Across the viewed start, transition and end states, do changing labels, visibility, focus and markers preserve identity and causality? Are success, retry and exit conditions still understandable while paused? State which intervening times were not viewed. |

For **PPT assets**, open the requested SVG at its allocated slide size and inspect the directions and context needed for that single state. A 1280px full-slide reference does not cover a smaller local asset. For **web illustrations**, inspect at the column width (720px if explicitly recorded as the assumption), with the surrounding prose's scope in mind. For **animation**, inspect the initial state, actual compiled beat boundaries, relevant transition midpoints and final state. For **paused interactive HTML**, inspect those states while paused. Seek backward to check content and camera reconstruction when the user requests interactive animation or the source includes state reset. Inspect the HTML controls separately from the diagram-only SVG.

Current sampling screenshots use a fixed inspection viewport. For actual SVG/PNG delivery, use [target-size artifact evidence](artifact-evidence.md). That workflow reads the exported file, records its target display surface and stores later actual-viewing attestations in `visual.artifactReviews`. Sampling `viewedFrames` covers only sampled images. Inspect paused HTML separately, and preserve the [source and information choices](source-fidelity.md) when proposing a readability correction.

## Save the later judgment

For SDK previews or saved HTML, follow [template selection and actual viewing](review-inputs.md#select-the-source-and-generate-a-template), then [submit the filled form](review-inputs.md#submit-filled-html-and-preview-forms). A changed diagram requires a separate authoring revision and new inspection of affected outputs.

`visual.viewedFrames` identifies original source images, times, paths, hashes and observations. `visual.review` identifies the submitting reviewer and source report. `checks.visual: reviewed` means only those source images were actually reported as viewed. It is not a blanket pass; issues become warnings awaiting the user's decision. Newly captured images remain unviewed. Changed source-image bytes, duplicate frame IDs, absent observations or an implicit parent are rejected.

## Editable page and narrow-screen inspection

Inspect the complete delivered HTML, including its heading, short introduction, functional reading hints, embedded diagram, captions, controls, spacing and responsive layout. Apply the [page completion checklist](delivery-contexts.md#page-completion-checklist) while viewing the outer page. The inspection report records actual visible caption/diagram text at requested compiled sample points with actual range progress (finite control precision), programmatic play/pause, backward reconstruction and outer static text stability. External network or local-file resource attempts fail offline inspection, even when blocked by the browser; retain successful files and report quality as incomplete. Keep CSS, scripts, fonts and images inline or in data URLs.

At narrow widths, keep the short introduction responsive and choose a diagram reading width based on the actual label sizes. The starter uses `--diagram-reading-width: 720px` within a keyboard-focusable horizontal scrolling region. This is an adjustable authoring starting point, not a readability threshold. Check both ends of the region, captions and access to controls; record viewport width and the actual playback width. Horizontal reading preserves objects and relationships but does not show the entire graph at once. Do not accept tiny labels merely because the whole SVG fits the phone viewport.
