# Screenshot capture and visual inspection

Default authoring captures the actual delivered HTML. View those saved images and revise the diagram as needed; capture alone does not establish viewing. Request SDK state previews with `--preview` only when they help a specific diagnosis. `--samples` bounds HTML captures. Formal registered review is separate and starts with an explicit `--formal-review` request or review operation; ordinary work needs no review form or unified quality pass.

Use `validate` while drafting. When intermediate HTML is needed, use `author --browser none`; capture the needed samples only after the draft is ready. Keep the same temporary `--output <task-workspace>/history` for generation and capture, then [finalize](tool-contract.md#finalize-the-task).

`author` attempts previews after default JSON/HTML, optional SVG and any requested GIF attempt. For independent stage failures and cancellation, see [partial delivery](export.md#partial-delivery-and-history). It uses the skill's explicit, locked `playwright-core` dependency inside the isolated runtime. It creates a dedicated browser, context and page; it neither connects to nor closes a browser owned by the host or user. Success, failure and cancellation close the resources the command created.

## Prepared browser

Pass `--browser <executable>` or set `FLOWSVG_BROWSER_PATH` to an installed Chrome/Chromium executable. An explicit path has priority. The tool verifies file readability and execution permission before launch; an unusable path fails visibly without creating a browser profile. Otherwise the tool detects standard macOS/Windows install locations or Linux executable names on `PATH`. `--browser none` disables detection. The tool never downloads a browser. Common executable paths are `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome` on macOS, `/usr/bin/chromium` on Linux and `C:\Program Files\Google\Chrome\Application\chrome.exe` on Windows; verify the actual path in this environment. Without one, default JSON/HTML and optional SVG still complete; screenshot capture and visual inspection remain unperformed. Install a browser separately when the user wants that check. Recapture HTML or SDK previews through `author` against current; collect missing formal SVG/PNG surfaces with independent [artifact evidence](artifact-evidence.md).

## Inspection-only preparation

For visual diagnosis without authoring changes, select the inspection source before viewing:

1. **Existing task evidence:** select current or an explicit retained checkpoint, name and output root through [input and parent selection](diagnostics-and-revisions.md#selecting-a-parent). Reuse its registered, readable HTML or preview screenshots for the requested scope. View actual SVG/PNG files at the intended dimensions and background; formal evidence capture is optional.
2. **JSON or a finalized delivery:** create a canonical [task workspace](tool-contract.md#task-workspace). Use the exact JSON bytes with `author --input <existing.json> --name <name> --output <task-workspace>/history --browser <prepared-executable>` to generate temporary HTML and screenshots. For a finalized Agent page, select its matching `diagram.html` with `--html` under [page continuation](tool-contract.md#continue-an-existing-page). These new captures cover the new files; historical exports or viewing records retain their original identity.
3. **Missing HTML or preview captures in an existing task:** run `author --from <selected-revision> --name <same-name> --output <same-task-workspace>/history --browser <prepared-executable>` to replace current captures from the unchanged JSON and inherited page. Use `--preview` only for SDK captures; retain explicit checkpoints when historical preservation was requested.

Keep the input design and bytes intact, including its effective theme; use the existing report's theme override when one was recorded. Run structural validation first when the input is unverified; blocking errors or an incompatible page stop capture and become diagnosis findings. If a browser or image viewer is unavailable, report the missing visual checks. View only the requested surfaces and report findings, files viewed and gaps. Register [review inputs](review-inputs.md) only for explicitly requested formal review. Inspection-only work stops there and retains its workspace; publishing a replacement or correcting the diagram requires authorization for that work.

## Reproducible samples

Actual HTML samples use compiled timeline times and preserve the authored camera, focus, visibility and content. Each time appears once. The initial and final states have priority, so animated `--samples 2` captures those two states when the duration is positive. Static diagrams have one state at zero. Request `--preview` for a separate SDK plan with a focus-free overview; that projection is not an actual HTML state. Neither a projected overview nor a timed export means “all objects visible.” If an all-visible composition requires changed meaning, confirm that meaning change before modifying the draft.

Additional candidates are content-change beat starts, transition midpoints, flow midpoints and other beat starts. Content changes have priority over midpoints and ordinary starts. For equal priority, earlier times have priority. Actual HTML uses at most 12 unique times by default; `author --samples <count>` selects a bound from 2 through 100. `htmlInspection.plan.omitted` lists candidates outside that bound. SDK `--preview` reserves one of its own slots for the overview. All intervening times remain unsampled; the plan is deterministic for the same input, compiler and sample count.

## Check the selected key stages

1. Choose the key stages needed to answer the reader's question: the initial state, important changes or transfers, and the final state. A key stage is an author-selected explanation checkpoint, not a requirement for one image per scene, beat or edge.
2. Read `compilation.beats` and `compilation.totalDurationMs` to locate those stages on the actual timeline. A single `flow` can replace its authored beat duration and shift later stages; see [effective flow duration](timeline.md#transfer-and-emphasis). For concurrent flows in one beat, one suitable image can cover the transfers when each route and marker is visible and distinguishable.
3. Compare each selected stage with `htmlInspection.plan.points`, `htmlInspection.plan.omitted` and `htmlInspection.states`. A separate SDK overview removes focus and cannot substitute for an actual HTML state. A planned point without a successful capture is still missing evidence.
4. For a missing stage, first try a larger `author --samples <count>` budget against current. Read the new plan and captures: a larger budget does not create arbitrary-time candidates. If the needed time is not a candidate or remains outside the supported budget, use an existing [timed SVG/PNG export](export.md#requested-svg-and-png) and view the actual export, or inspect the actual HTML at that time or through playback. Record the surface and time range checked; a formal image does not cover HTML controls, captions or continuous motion.
5. Actually view the selected images. New captures still require viewing, including recaptures of unchanged input. Explain viewed files and stages in the delivery message; put substantive findings in the single `issues.md`. No separate stage form or review submission is needed for default viewing.

Finish this check when every selected stage has identified viewed evidence, or an explicit gap and its effect on the explanation. If supplementation cannot be completed, disclose the missing stage and affected surface or interval. State the actual viewing scope and remaining effects; this check adds no score or approval gate. Programmatic time and identity checks establish those facts, while actual viewing supports judgments about readability, whitespace and narrative continuity. Assess pacing through actual playback and report sample-only inspection as limited to the viewed states.

## Actual offline HTML

For Agent-composed pages, inspect the whole outer page and its declared embedded player. Page headings, the short introduction, functional reading hints, spacing and responsive layout are part of HTML viewing; controls and SVG state are checked inside the managed frame. During Agent self-check, apply the [page completion checklist](delivery-contexts.md#page-completion-checklist). If the page contains a block outside the closed whitelist, describe it as an authoring issue and move or remove it before delivery; this is a review instruction, not a CLI or report validation rule. Captures and hashes identify the complete final HTML, not only the iframe content.

When HTML is part of the requested delivery, `author` opens the saved `diagram.html` in an owned offline browser context after writing it. The report records the exact HTML SHA-256, input/SDK/theme context, viewport and background, initial paused state, control values, external requests, playback advancement and screenshots for the same static or compiled timeline points. These facts describe the file and browser behavior; they do not mean a model viewed the screenshots. Record actual viewing through [Save the later judgment](#save-the-later-judgment). A missing browser leaves `checks.html: not-run` with an explicit reason.

Each captured point renders the public SDK SVG state at exact milliseconds, explicit theme and full motion. Playwright uses a 1440 × 1000 viewport, device scale factor 1, offline context and a dedicated static document. Capture waits for `document.fonts.ready`. Images use system fonts; the report records observed font readiness, font family and font-face errors. A ready font set does not prove every Chinese glyph exists. Missing glyphs, reading difficulty and platform differences require actual image inspection. Cross-system pixel equality is not promised.

## Actual model inspection

View actual saved PNGs through the host's image viewer or attachments. If unavailable, explain the missing viewing scope and its effect. Start with the initial actual HTML state, then inspect needed timeline states. Assess reading order, density, occlusion and narrative continuity against the question and display conditions. Successful capture or nonempty PNG bytes cannot establish visual quality.

Correct problems within the authorized meaning, regenerate current outputs and re-view affected states. Keep material findings and their handling in `issues.md`; disclose retained issues and viewing gaps at delivery. SDK preview viewing covers only that sampled diagram surface. HTML controls/page layout and actual SVG/PNG files need their own viewing.

## Questions for the four observations

Use these questions as design guidance while viewing. Record substantive findings in the task's single `issues.md`; a four-field observation form is needed only when explicitly registering formal review.

| Field | Inspection questions |
| --- | --- |
| `readingOrder` | Can the reader identify the entry point, then trace each relevant arrow from its source through bends or shared segments to its arrowhead? In regular layouts, would alignment or a simple right-angle path improve a long diagonal? Do bent paths introduce excessive detours or ambiguous shared segments? Do group and component endpoints match the selected relationship scope? In a layer overview, are component exceptions justified? Are request and return directions distinct? Do boundary headings explain membership? Can the reader recover the direction after a crossing? |
| `density` | At the intended display width, can the reader distinguish labels, conditions and units? Does the slide's occupied area or article column leave enough space? Are short-content nodes oversized, or does their whitespace serve comparison, later animation content or the composition? Record actual or assumed dimensions. A higher-resolution file does not enlarge text displayed at the same width. Node count is a prompt to assess readability, never permission to delete information. |
| `occlusion` | Does a connection cross an unrelated node in a way that suggests a false relationship? Do long coincident paths hide independent edges, merge solid and dashed meanings or suggest an unsupported junction? Can each edge be followed through the busy channel in an actual crop? Does an edge label cover an unrelated node, another label or a needed arrowhead? Are text, group titles and ports clipped or covered? Distinguish intended containment and endpoint contact from obscured meaning. A crossing alone need not be an error. |
| `narrative` | Does the shown state match the selected time, caption and explanation? Across the viewed start, transition and end states, do changing labels, visibility, focus and markers preserve identity and causality? Are success, retry and exit conditions still understandable while paused? State which intervening times were not viewed. |

For **PPT assets**, open the requested SVG at its allocated slide size and inspect the directions and context needed for that single state. A 1280px full-slide reference does not cover a smaller local asset. For **web illustrations**, inspect at the column width (720px if explicitly recorded as the assumption), with the surrounding prose's scope in mind. For **animation**, inspect the initial state, actual compiled beat boundaries, relevant transition midpoints and final state. For **paused interactive HTML**, inspect those states while paused. Seek backward to check content and camera reconstruction when the user requests interactive animation or the source includes state reset. Inspect the HTML controls separately from the diagram-only SVG.

Sampling screenshots use a fixed inspection viewport. Open actual SVG/PNG delivery files at their intended size and background. Explicit formal review can add [target-size artifact evidence](artifact-evidence.md); registered sampled viewing covers only its sampled images. Inspect paused HTML separately, and preserve the [source and information choices](source-fidelity.md) when proposing a readability correction.

## Save the later judgment

Default viewing conclusions belong in the final delivery message: identify files, display dimensions, animation stages and any gaps. Work findings remain in `issues.md`, with unresolved effects summarized for `finalize --notes`. Capture status `captured` describes generated materials, not actual viewing.

For an explicit formal request, read [review input contracts](review-inputs.md), fix a stable source with `author --formal-review`, and use its returned `v###` for evidence, templates and review. Fill observations only for images actually viewed. Valid records establish identity and declared coverage; viewer conclusions and unresolved issues remain separately attributed. Regenerated current output does not inherit old viewing claims.

## Editable page and narrow-screen inspection

Inspect the complete delivered HTML, including its heading, short introduction, functional reading hints, embedded diagram, captions, controls, spacing and responsive layout. Apply the [page completion checklist](delivery-contexts.md#page-completion-checklist) while viewing the outer page. The inspection report records actual visible caption/diagram text at requested compiled sample points with actual range progress (finite control precision), programmatic play/pause, backward reconstruction and outer static text stability. External network or local-file resource attempts fail offline inspection, even when blocked by the browser; retain successful files and report the failed offline check. Formal coverage, when requested, remains incomplete for that scope. Keep CSS, scripts, fonts and images inline or in data URLs.

At narrow widths, keep the short introduction responsive and choose a diagram reading width based on the actual label sizes. The starter uses `--diagram-reading-width: 720px` within a keyboard-focusable horizontal scrolling region. This is an adjustable authoring starting point, not a readability threshold. Check both ends of the region, captions and access to controls; record viewport width and the actual playback width. Horizontal reading preserves objects and relationships but does not show the entire graph at once. Do not accept tiny labels merely because the whole SVG fits the phone viewport.
